    23. Ejercicio práctico – Versión 12

    En este capítulo, escribiremos una aplicación web que siga la arquitectura MVC (Modelo-Vista-Controlador). La aplicación podrá devolver respuestas en tres formatos: JSON, XML y HTML. Hay un aumento significativo de la complejidad entre lo que estamos a punto de hacer y lo que hemos hecho anteriormente. Reutilizaremos la mayoría de los conceptos tratados hasta ahora y detallaremos todos los pasos que conducen a la aplicación final.

    23.1. Arquitectura MVC

    Implementaremos el patrón arquitectónico MVC (Modelo-Vista-Controlador) de la siguiente manera:

    El procesamiento de una solicitud del cliente se llevará a cabo de la siguiente manera:

    • 1 - Solicitud

    Las URL solicitadas tendrán el formato http://machine:port/contexte/….?action=anAction&param1=v1&param2=v2&… El [Controlador principal] utilizará un archivo de configuración para «enrutar» la solicitud al controlador correcto y a la acción correcta dentro de ese controlador. Para ello, utilizará el campo [action] de la URL. El resto de la URL [param1=v1&param2=v2&…] consiste en parámetros opcionales que se pasarán a la acción. La C de MVC aquí es la cadena [Controlador principal, Controlador / Acción]. Si ningún controlador puede gestionar la acción solicitada, el servidor web responderá que no se ha encontrado la URL solicitada.

    • 2 - Procesamiento
      • La acción seleccionada [2a] puede utilizar los parámetros que le ha pasado el [Controlador principal]. Estos pueden provenir de varias fuentes:
        • la ruta [/param1/param2/…] de la URL,
        • los parámetros de la URL [param1=v1&param2=v2],
        • los parámetros enviados por el navegador con su solicitud;
      • Al procesar la solicitud del usuario, la acción puede requerir la capa [de negocio] [2b]. Una vez procesada la solicitud del cliente, puede desencadenar diversas respuestas. Un ejemplo clásico es:
        • una respuesta de error si la solicitud no se ha podido procesar correctamente;
        • una respuesta de confirmación en caso contrario;
      • el [Controlador / Acción] devolverá su respuesta [2c] al controlador principal junto con un código de estado. Estos códigos de estado representarán de forma única el estado de la aplicación. Serán códigos de éxito o códigos de error;
    • 3 - Respuesta
      • Dependiendo de si el cliente solicitó una respuesta JSON, XML o HTML, el [Controlador principal] instanciará [3a] el tipo de respuesta adecuado y le indicará que envíe la respuesta al cliente. El [Controlador principal] le pasará tanto la respuesta como el código de estado proporcionado por el [Controlador/Acción] que se ejecutó;
      • si la respuesta deseada es de tipo JSON o XML, la respuesta seleccionada formateará la respuesta del [Controlador/Acción] que se le proporcionó y la enviará [3c]. El cliente capaz de procesar esta respuesta puede ser un script de consola PHP o un script JavaScript incrustado en una página HTML;
      • Si la respuesta deseada es de tipo HTML, la respuesta seleccionada elegirá [3b] una de las vistas HTML [Vuei] utilizando el código de estado que se le ha proporcionado. Esta es la «V» de MVC. Una sola vista corresponde a un código de estado. Esta vista V mostrará la respuesta del [Controlador/ Acción] que se ejecutó. Envuelve los datos de esta respuesta en HTML, CSS y JavaScript. Estos datos se denominan modelo de vista. Esta es la «M» de MVC. El cliente suele ser un navegador;

    Ahora, aclaremos la relación entre la arquitectura web MVC y la arquitectura por capas. Dependiendo de cómo se defina el modelo, estos dos conceptos pueden estar relacionados o no. Consideremos una aplicación web MVC de una sola capa:

    En el ejemplo anterior, tanto el [Controlador] como la [Acción] incorporan partes de las capas [de negocio] y [DAO]. En la capa [web] sí que tenemos una arquitectura MVC, pero la aplicación en su conjunto no presenta una arquitectura por capas. En este caso, solo hay una capa que se encarga de todo.

    Ahora, consideremos una arquitectura web de múltiples capas:

    La capa [Web] se puede implementar sin seguir el modelo MVC. Entonces tenemos una arquitectura de múltiples capas, pero la capa Web no implementa el modelo MVC.

    Por ejemplo, en el entorno .NET, la capa [web] anterior se puede implementar con ASP.NET MVC, lo que da como resultado una arquitectura en capas con una capa [web] de estilo MVC. Una vez hecho esto, podemos sustituir esta capa ASP.NET MVC por una capa ASP.NET clásica (WebForms) sin modificar el resto (lógica de negocio, DAO, controlador). De este modo, obtenemos una arquitectura en capas con una capa [web] que ya no se basa en MVC.

    En MVC, dijimos que el modelo M era el de la vista V, es decir, el conjunto de datos mostrados por la vista V. Se ofrece otra definición del modelo M en MVC:

    Muchos autores consideran que lo que se encuentra a la derecha de la capa [web] constituye el modelo M de MVC. Para evitar ambigüedades, podemos referirnos a:

    • el modelo de dominio cuando nos referimos a todo lo que se encuentra a la derecha de la capa [web];
    • el modelo de vista cuando nos refiramos a los datos mostrados por una vista V;

    23.2. Árbol de proyectos de NetBeans

    Para el proyecto NetBeans, adoptaremos una arquitectura que refleje el modelo MVC:

    • [3]: [main.php] es el controlador principal de nuestro modelo MVC. Es la C de MVC;
    • [4]: La carpeta [Controllers] contendrá los controladores secundarios. Cada uno gestiona una acción específica. Esta acción se indica en la URL, por ejemplo […/main.php?action=authenticate-user]. Con esta acción, el [Controlador principal] [main.php] seleccionará un [Controlador secundario], en este caso [AuthentifierUtilisateurController], para gestionar la acción solicitada. Estos controladores también forman parte de la C de MVC;
    • [5]: La carpeta [Model] contendrá las capas [business] y [DAO] de la aplicación. Según los términos adoptados anteriormente, estos elementos representan el modelo de dominio y, según la terminología adoptada para la M, pueden representar la M en MVC;
    • [6]: La carpeta [Responses] contiene las clases encargadas de enviar la respuesta al cliente. Hay una clase por cada tipo de respuesta deseado:
      • [JsonResponse]: para una respuesta JSON;
      • [XmlResponse]: para una respuesta XML;
      • [HtmlResponse]: para una respuesta HTML;
    • [7]: La carpeta [Views] contiene las vistas HTML cuando se desea una respuesta HTML. Esta es la V en MVC. Son activadas por la clase [HtmlResponse], que les pasa los datos a mostrar. Estos datos son el modelo de vista. Dependiendo de la terminología adoptada para la M, estos datos pueden representar la M en MVC;
    • [8]: La carpeta [Utilities] contiene programas de utilidad:
      • [Logger]: la clase que permite registrar datos en un archivo de texto;
      • [Sendmail]: la clase que permite enviar correos electrónicos;
    • [9]: La carpeta [Logs] contiene el archivo de registro [logs.txt];
    • [10]: La carpeta [Entities] contiene las clases que utilizan los distintos controladores;

    Utilizando esta estructura de directorios, podemos describir el flujo de procesamiento de una acción solicitada por un cliente:

    • [main.php] [3] recibe la solicitud;
    • tras realizar algunas comprobaciones preliminares (¿es la acción una de las aceptadas?), reenvía la solicitud al controlador secundario [4] responsable de procesar esta acción;
    • el controlador secundario realiza su tarea. Para ello, puede necesitar las capas [business] y [DAO] [5], así como entidades de la carpeta [10]. Devuelve su respuesta al controlador principal [main.php] que lo activó;
    • dependiendo del tipo de respuesta [JSON, XML, HTML] solicitada por el cliente, el controlador principal [main.php] activa una de las respuestas de la carpeta [Responses] [6];
    • las respuestas [JsonResponse] y [XmlResponse] envían la respuesta JSON o XML al cliente, respectivamente;
    • [HtmlResponse] utiliza una de las vistas de la carpeta [Views] [7] para enviar una respuesta HTML al cliente;
    • Los distintos controladores tienen acceso a la clase [Logger] de la carpeta [8] para escribir registros en el archivo de registro de la carpeta [9]. Se registran los siguientes datos:
      • la acción solicitada;
      • la respuesta del controlador. Esta se registra en formato JSON independientemente del tipo solicitado [JSON, XML, HTML];
    • en caso de un error fatal (HTTP_INTERNAL_SERVER_ERROR), el controlador principal [main.php] envía un correo electrónico al administrador utilizando la clase [SendMail] de la carpeta [8];

    23.3. Acciones de la aplicación

    El cliente envía la acción que se va a ejecutar al servidor web como un parámetro [action] en la URL [/main.php?action=xxx]. Las acciones permitidas se enumeran en el archivo [config.json] que configura el controlador principal [main.php]:

    
"actions":
            {
                "init-session": "\\InitSessionController",
                "authentifier-utilisateur": "\\AuthentifierUtilisateurController",
                "calculer-impot": "\\CalculerImpotController",
                "lister-simulations": "\\ListerSimulationsController",
                "supprimer-simulation": "\\SupprimerSimulationController",
                "fin-session": "\\FinSessionController",
                "afficher-calcul-impot": "\\AfficherCalculImpotController"
},
    • línea 1: la clave [actions] del diccionario JSON;
    • líneas 3–9: un diccionario [action:controller]. Cada acción está asociada al controlador secundario responsable de procesarla;
    • línea 3: [init-session]: inicia una sesión de simulaciones de cálculo de impuestos. Esta acción especifica el tipo de respuesta deseado [JSON, XML, HTML];
    • línea 4: una vez establecido el tipo de sesión, el cliente debe autenticarse mediante la acción [authenticate-user]. Hasta que el cliente se haya autenticado, todas las demás acciones están prohibidas, excepto [init-session];
    • línea 5: una vez autenticado, el cliente puede realizar una serie de cálculos de impuestos mediante la acción [calculate-tax];
    • línea 6: en cualquier momento, el cliente puede solicitar ver la lista de simulaciones que ha realizado mediante la acción [list-simulations];
    • línea 7: puede eliminar algunas de ellas mediante la acción [delete-simulation];
    • línea 8: el cliente finaliza su sesión de simulación mediante la acción [end-session]. A partir de ese momento, deberá volver a iniciar sesión si desea utilizar la aplicación;
    • línea 9: En la aplicación HTML, la acción [display-tax-calculation] muestra el formulario utilizado para calcular el impuesto;

    23.5. Instalación de herramientas y bibliotecas

    23.5.1. Postman

    [Postman] es la herramienta que nos permitirá consultar las distintas URL de nuestra aplicación web. Nos permite:

    • utilizar cualquier URL: estas se crean manualmente;
    • consultar el servidor web utilizando GET, POST, PUT, OPTIONS, etc.;
    • especificar parámetros GET o POST;
    • configurar los encabezados HTTP de la solicitud;
    • recibir una respuesta en formato JSON, XML o HTML;
    • acceder a los encabezados HTTP de la respuesta. Esto nos permite acceder a la respuesta HTTP completa del servidor;

    Dado que estamos construyendo manualmente las URL que se consultan, podremos probar todos los posibles escenarios de error y ver cómo reacciona el servidor.

    [Postman] está disponible en la URL [https://www.getpostman.com/downloads/]. La versión disponible en junio de 2019 es la 7.2. Esta versión tiene un error: al realizar solicitudes sucesivas al servidor web, el cliente [Postman 7.2] no devuelve automáticamente las cookies enviadas por el servidor, en particular la cookie de sesión. Para mantener la sesión, hay que copiar manualmente la cookie de sesión en los encabezados HTTP de las solicitudes posteriores. No es muy complicado, pero tampoco es práctico. Se trata de un error que no existía en versiones anteriores. Consciente del error, el equipo de [Postman] lo ha corregido en una versión alfa (que puede ser inestable) llamada [Postman Canary], disponible en la URL [https://www.getpostman.com/downloads/canary]. Esta es la versión que se utiliza aquí. Describiremos cómo instalarla. Si hay disponible una versión estable [Postman 7.3] o posterior, puedes descargarla: es probable que el error ya se haya corregido.

    Continúe con la instalación de su versión de [Postman]. Durante la instalación, se le pedirá que cree una cuenta: esto no será necesario aquí. La cuenta de [Postman] se utiliza para sincronizar diferentes dispositivos, de modo que la configuración de uno se replique en otro. Nada de esto es necesario aquí.

    Una vez instalado, [Postman] muestra la siguiente interfaz:

    • en [2-3], puedes acceder a la configuración del producto;

    • en [6], la versión utilizada en este documento;
    • si ha creado una cuenta, se produce una sincronización entre su ordenador y un servidor remoto de [Postman]. Esto se indica mediante la rueda giratoria [7] que aparece cada vez que realiza cambios en el proyecto de [Postman]. Para detener esta sincronización innecesaria, cierre la sesión a través de [8-9];

    23.5.2. La biblioteca Symfony / Serializer

    Para serializar objetos en JSON y XML, utilizaremos la biblioteca [Symfony / Serializer]. Ofrece dos ventajas en este caso:

    • es coherente en su uso para la serialización a JSON o XML: esto evita tener que aprender dos bibliotecas con diferentes API (interfaces de programación de aplicaciones);
    • de forma nativa, puede serializar objetos a JSON o XML, incluso si sus atributos son privados. Recuerda que en JSON, para serializar un objeto, su clase tenía que implementar la interfaz [\JsonSerializable]. El resultado obtenido era una cadena JSON de un array asociativo con los atributos de la clase como claves. Al deserializar esta cadena JSON, recuperábamos el array asociativo primitivo, que luego tenía que convertirse en un objeto de la clase que se había serializado.       • todos los parámetros esperados son cadenas, mientras que una función puede especificar el tipo de sus parámetros. Si el parámetro esperado es un número, debes verificar que la cadena del parámetro sea efectivamente la de un número;

    Request $request,
    Session $session,

    $method = strtolower($request->getMethod());
    $erreur = $method !== "get" || $request->query->count() != 2;
    if ($erreur) {
      $état = 701;
      $message = "méthode GET exigée avec paramètres [action, type] dans l'URL";
      return [Response::HTTP_BAD_REQUEST, $état, ["réponse" => $message], []];

    $erreur = FALSE;

    if (!$request->query->has("type")) {
      $erreur = TRUE;
      $état = 702;
      $message = "paramètre [type] manquant";
    } else {
      $type = strtolower($request->query->get("type"));
    }
    // type verification
    if (!$erreur && !array_key_exists($type, $config["types"])) {
      $erreur = TRUE;
      $état = 703;
      $message = "paramètre type [$type] invalide";
    }
    // mistake?
    if ($erreur) {
      return [Response::HTTP_BAD_REQUEST, $état, ["réponse" => $message], []];
    }
    // put the session type in the session
    $session->set("type", $type);
    // message of success
    $message = "session démarrée avec type [$type]";
    $état = 700;
    return [Response::HTTP_OK, $état, ["réponse" => $message], []];
  }

    Repasemos ahora el código de la clase [ParentResponse], la clase padre de los tres tipos de respuesta que abstrae lo que tienen en común: el envío real de una respuesta de texto al cliente:

    
<?php
 
namespace Application;
 
// symfony dependencies
use Symfony\Component\HttpFoundation\Response;
 
class ParentResponse {
 
  // int $statusCode: HTTP response status code
  // string $content: the body of the response to be sent
  // depending on the case, this is a jSON, XML, HTML string
  // array $headers: HTTP headers to be added to the response
 
  public function sendResponse(
    int $statusCode,
    string $content,
    array $headers): void {
 
    // preparing the server's text response
    $response = new Response();
    $response->setCharset("utf-8");
    // status code
    $response->setStatusCode($statusCode);
    // headers
    foreach ($headers as $text => $value) {
      $response->headers->set($text, $value);
    }
    // we send the answer
    $response->setContent($content);
    $response->send();
  }
}

    • línea 22: la respuesta contendrá caracteres UTF-8;
    • línea 24: código de estado HTTP de la respuesta;

use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

use \Symfony\Component\HttpFoundation\Session\Session;

  // Session $session: the web application session
  // array $config: application configuration
  // int statusCode: HTTP response status code
  // array $content: server response
  // array $headers: HTTP headers to be added to the response

    Session $session = NULL,
    array $config,
    int $statusCode,
    array $content,
    array $headers,
    Logger $logger = NULL): void {

    $serializer = new Serializer(
      [
      // required for object serialization
      new ObjectNormalizer()],
      // encoder jSON

      [new JsonEncoder(new JsonEncode([JsonEncode::OPTIONS => JSON_UNESCAPED_UNICODE]))]

namespace Application;
 
// symfony dependencies
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Session\Session;
use Symfony\Component\Serializer\Encoder\JsonEncode;
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;
 
class HtmlResponse extends ParentResponse implements InterfaceResponse {
 
  // Request $request : requête en cours de traitement
  // Session $session: the web application session
  // array $config: application configuration
  // int statusCode: HTTP response status code
  // array $content: server response
  // array $headers: HTTP headers to be added to the response
  // Logger $logger: the logger for writing logs
 
  public function send(
    Request $request = NULL,
    Session $session = NULL,
    array $config,
    int $statusCode,
    array $content,
    array $headers,
    Logger $logger = NULL): void {
 
    // symfony serializer preparation
    $serializer = new Serializer(
      [
      // for object serialization
      new ObjectNormalizer()],
      [
      // for jSON serialization of the response log
      new JsonEncoder(new JsonEncode([JsonEncode::OPTIONS => JSON_UNESCAPED_UNICODE]))
      ]
    );
    // the HTML response depends on the status code returned by the controller
    $état = $content["état"];
    // a view corresponds to a state - look for it in the application configuration
    // view list
    $vues = array_keys($config["vues"]);
    $trouvé = false;
    $i = 0;
    // browse the list of views
    while (!$trouvé && $i < count($vues)) {
      // states associated with view n° i
      $états = $config["vues"][$vues[$i]];
      // is the state you're looking for in the states associated with view n° I?
      if (in_array($état, $états)) {
        // the view displayed will be view n° i
        $vueRéponse = $vues[$i];
        $trouvé = true;
      }
      // next view
      $i++;
    }
    // found?
    if (!$trouvé) {
      // if no view exists for the current state of the application
      // render error view
      $vueRéponse = $config["vue-erreurs"];
    }
    // retrieve the HTML view to be displayed in a character string
    ob_start();
    require __DIR__ . "/../Views/$vueRéponse";
    $html = ob_get_clean();
    // we indicate in the headers that we're going to send HTML
    $headers = array_merge($headers, ["content-type" => "text/html"]);
    // the parent class handles the actual sending of the response
    parent::sendResponse($statusCode, $html, $headers);
    // log in jSON of the response without the HTML
    if ($logger !== NULL) {
      // log in jSON of the response from the secondary controller that processed the action
      $log = $serializer->serialize($content, 'json');
      $logger->write("réponse=$log\n");
    }
  }
 
}

          $this->sessionCookie = "PHPSESSID=" . $champs[1];
        }
      }
    }
  }

    Dado que la acción [init-session] debe ser la primera acción solicitada al servicio web, el método [initSession] será el primer método de la capa [dao] en ser invocado.

    • línea 1: se pasa el tipo de sesión deseado como parámetro. Si no se proporciona ningún parámetro, se iniciará una sesión JSON;
    • líneas 5–11: se realiza una solicitud GET al servicio web;
    • líneas 7-8: los dos parámetros GET;
    • línea 10: en el caso de una comunicación segura (HTTPS), no se verificará el certificado de seguridad enviado por el servicio web;
    • línea 13: el método [getResponse] recupera la respuesta del servidor. La devuelve en forma de matriz. En este caso, no se utiliza el resultado del método. El método [getResponse] lanza una excepción si el código de estado HTTP de la respuesta del servicio web no es 200 OK;

    23.14.2.2.2. El método [getResponse]

    El método [getResponse] se encarga de procesar la respuesta del servicio web:

    
private function getResponse(CurlResponse $response) {
    // the answer is retrieved
    $json = $response->getContent(false);
    // logs
    if ($this->verbose) {
      print "$json\n";
    }
    // retrieve response status
    $statusCode = $response->getStatusCode();
    // mistake?
    if ($statusCode !== 200) {
      // we have an error
      throw new ExceptionImpots($json);
    }
    // we give our answer
    $array = json_decode($json, true);
    return $array["réponse"];
  }

    Comentarios

    • línea 1: el método es privado;
    • línea 1: el parámetro del método es la respuesta del servicio web de tipo [Symfony\Component\HttpClient\Response\CurlResponse], el tipo de respuesta de Symfony, cuando [HttpClient] está implementado por [CurlClient], es decir, por la biblioteca [curl];

    • líneas 9–14: si el estado de la respuesta HTTP del servidor no es 200, se lanza una excepción con la respuesta JSON del servidor como mensaje de error;

<?php
 
namespace Application;

  // batch mode tax calculation
  public function executeBatchImpots(string $taxPayersFileName, string $resultsFileName, string $errorsFileName): void {
    // we let the exceptions coming from the [dao] layer flow upwards
    // retrieve taxpayer data
    $taxPayersData = $this->clientDao->getTaxPayersData($taxPayersFileName, $errorsFileName);

    }
  }

    $this->clientDao->authentifierUtilisateur($user, $password);

    $this->clientDao->saveResults($resultsFilename, $simulations);

    return $this->clientDao->supprimerSimulation($numéro);

  }
