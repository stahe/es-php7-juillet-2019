    17. Servicios web

    Nota: Por «servicio web» nos referimos aquí a cualquier aplicación web que proporcione datos sin procesar consumidos por un cliente —un script de consola en los ejemplos que siguen—. No nos ocupamos de ninguna tecnología en particular —REST (REpresentational State Transfer) o SOAP (Simple Object Access Protocol), por ejemplo— que proporcione datos más o menos sin procesar en un formato bien definido. REST devuelve JSON, mientras que SOAP devuelve XML. Cada una de estas tecnologías define con precisión cómo debe consultar el cliente al servidor y el formato que debe adoptar la respuesta del servidor. En este curso, seremos mucho más flexibles en cuanto a la naturaleza de la solicitud del cliente y la respuesta del servidor. Sin embargo, los scripts escritos y las herramientas utilizadas son similares a los de la tecnología REST.

    17.1. Introducción

    Dado que los programas PHP pueden ser ejecutados por un servidor web, dicho programa se convierte en un programa del lado del servidor capaz de atender a múltiples clientes. Desde la perspectiva del cliente, llamar a un servicio web equivale a solicitar la URL de dicho servicio. El cliente puede estar escrito en cualquier lenguaje, incluido PHP. En este último caso, utilizamos las funciones de red que acabamos de ver. También necesitamos saber cómo «comunicarnos» con un servicio web, es decir, comprender el protocolo HTTP para la comunicación entre un servidor web y sus clientes. Ese era el propósito de la sección «enlace».

    El cliente web descrito en la sección «enlace» nos permitió explorar parte del protocolo HTTP.

    En su forma más simple, los intercambios entre cliente y servidor se desarrollan de la siguiente manera:

    • el cliente abre una conexión al puerto 80 del servidor web;
    • solicita un documento;
    • el servidor web envía el documento solicitado y cierra la conexión;
    • a continuación, el cliente cierra la conexión;

    El documento puede ser de varios tipos: texto en formato HTML, una imagen, un vídeo… Puede ser un documento ya existente (documento estático) o un documento generado sobre la marcha por un script (documento dinámico). En este último caso, hablamos de programación web. El script para generar documentos dinámicamente puede estar escrito en varios lenguajes: PHP, Python, Perl, Java, Ruby, C#, VB.NET…

    A continuación, utilizaremos scripts PHP para generar dinámicamente documentos de texto.

    • En [1], el cliente establece una conexión con el servidor, solicita un script PHP y puede enviar o no parámetros a dicho script;
    • En [2], el servidor web ejecuta el script PHP utilizando el intérprete de PHP. El script genera un documento que se envía al cliente [3];
    • El servidor cierra la conexión. El cliente hace lo mismo;

    El servidor web puede gestionar varios clientes a la vez.

    17.4. Conceptos básicos de HTML

    Este capítulo no profundizará en la programación web en PHP. En la sección enlazada se desarrolla una aplicación web MVC. En cambio, este capítulo se centra en los servicios web: páginas PHP que envían datos, a través de un servidor web, a otros clientes PHP. No obstante, nos ha parecido útil proporcionar al lector algunos conceptos básicos de HTML.

    Un navegador web puede mostrar diversos documentos, siendo los más comunes los documentos HTML (HyperText Markup Language). Estos consisten en texto formateado con etiquetas de la forma <etiqueta>texto</etiqueta>. Así, el texto <b>importante</b> mostrará la palabra «importante» en negrita. Existen etiquetas independientes, como la etiqueta <hr/>, que muestra una línea horizontal. No repasaremos todas las etiquetas que pueden encontrarse en un texto HTML. Existen muchos programas de software WYSIWYG que te permiten crear una página web sin escribir una sola línea de código HTML. Estas herramientas generan automáticamente el código HTML para un diseño creado con el ratón y controles predefinidos. Así, puedes insertar (con el ratón) una tabla en la página y luego ver el código HTML generado por el software para descubrir las etiquetas que se deben usar para definir una tabla en una página web. Es tan sencillo como eso. Además, el conocimiento de HTML es esencial, ya que las aplicaciones web dinámicas deben generar ellas mismas el código HTML para enviarlo a los clientes web. Este código se genera mediante programación y, por supuesto, debes saber qué generar para que el cliente reciba la página web que desea.

    En resumen, no es necesario conocer todo el lenguaje HTML para iniciarse en la programación web. Sin embargo, estos conocimientos son necesarios y se pueden adquirir utilizando editores de páginas web WYSIWYG como DreamWeaver y muchos otros. Otra forma de descubrir las complejidades del HTML es navegar por la web y ver el código fuente de páginas que contengan elementos interesantes con los que aún no te hayas encontrado.

    Considera el siguiente ejemplo, que destaca algunos elementos que se encuentran habitualmente en un documento web, tales como:

    • una tabla;
    • una imagen;
    • un enlace.

    Un documento HTML suele tener la siguiente estructura:

    <html> <head> <title>Un título</title> ... </head> <atributos del cuerpo> ... </body></html>

    Todo el documento está entre las etiquetas <html>…</html>. Consta de dos partes:

    1. <head>…</head>: esta es la parte no visible del documento. Proporciona información al navegador que mostrará el documento. A menudo contiene la etiqueta <title>…</title>, que establece el texto que se mostrará en la barra de título del navegador. También puede contener otras etiquetas, en particular las que definen las palabras clave del documento, que luego utilizan los motores de búsqueda. Esta sección también puede contener scripts, normalmente escritos en JavaScript o VBScript, que serán ejecutados por el navegador.
    1. <atributos del cuerpo>…</body>: Esta es la sección que mostrará el navegador. Las etiquetas HTML contenidas en esta sección indican al navegador el diseño visual «deseado» para el documento. Cada navegador interpreta estas etiquetas a su manera. Como resultado, dos navegadores pueden mostrar el mismo documento web de forma diferente. Este es, por lo general, uno de los retos a los que se enfrentan los diseñadores web.

    17.7. Un servidor de datos JSON

    La respuesta de un script web puede constar de múltiples puntos de datos que se pueden organizar en matrices y objetos. A continuación, el script puede enviar estos diversos elementos dentro de una cadena JSON que el cliente descodificará.

    17.7.1. El script del servidor

    El script [json-server.php] utiliza la siguiente clase [Person]:

    
<?php
 
namespace Modèles;
 
class Personne implements \JsonSerializable {
  // attributes
  private $nom;
  private $prénom;
  private $âge;
 
  // convert associative array to object [Person]
  public function setFromArray(array $assoc): Personne {
    // initialize the current object with the associative array
    foreach ($assoc as $attribute => $value) {
      $this->$attribute = $value;
    }
    // result
    return $this;
  }

  // getters and setters
  public function getNom() {
    return $this->nom;
  }
 
  public function getPrénom() {
    return $this->prénom;
  }
 
  public function setNom($nom) {
    $this->nom = $nom;
    return $this;
  }
 
  public function setPrénom($prénom) {
    $this->prénom = $prénom;
    return $this;
  }
 
  public function getÂge() {
    return $this->âge;
  }
 
  public function setÂge($âge) {
    $this->âge = $âge;
    return $this;
  }
 
  // toString
  public function __toString(): string {
    return "Personne [$this->prénom, $this->nom, $this->âge]";
  }
 
  // implements the JsonSerializable interface
  public function jsonSerialize(): array {
    // render an associative array with the object's attributes as keys
    // this table can then be encoded as jSON
    return get_object_vars($this);
  }
 
  // convert a jSON to a [Person] object
  public static function jsonUnserialize(string $json): Personne {
    // we create a person from the string jSON
    return (new Personne())->setFromArray(json_decode($json, true));
  }
 
}

    Comentarios

    • línea 5: la clase implementa la interfaz [JsonSerializable] de PHP. Esto requiere que implemente el método [jsonSerialize] en las líneas 55–59. El método debe devolver un array asociativo que se serializará en JSON.     • Líneas 12–19: La clase no tiene un constructor, pero sí un inicializador. La clase [Person] puede entonces instanciarse utilizando la expresión [(new Person()) → setFromArray($array)].     17.9. Recuperación por parte del servidor de los parámetros enviados por un cliente

    17.9.1. Introducción

    En el protocolo HTTP, un cliente dispone de dos métodos para pasar parámetros al servidor web:

    • solicita la URL del servicio en el formulario 
    
GET url?param1=val1&param2=val2&param3=val3… HTTP/1.0

    donde los valores válidos deben codificarse primero para que ciertos caracteres reservados sean sustituidos por sus valores hexadecimales;

    • solicita la URL del servicio en el formato 
    
POST url HTTP/1.0

    entonces, entre los encabezados HTTP enviados al servidor, se incluye el siguiente encabezado:

    Content-length=N

    El resto de los encabezados enviados por el cliente terminan con una línea en blanco. A continuación, puede enviar sus datos en el formato

    val1&param2=val2&param3=val3…

    donde los valores válidos deben, al igual que con el método GET, codificarse previamente. El número de caracteres enviados al servidor debe ser N, donde N es el valor declarado en el encabezado

    Content-length=N

    El script PHP del servicio web que recupera los parámetros parami enviados previamente por el cliente obtiene sus valores de la matriz:

    • $_GET["parami"] para una solicitud GET;
    • $_POST["parami"] para una solicitud POST;

    Esto se aplica a las funciones básicas de PHP. Si se utiliza la biblioteca [HttpFoundation], estos parámetros se encontrarán en:

    • [Request]->query->get('parami') para una solicitud GET;
    • [Request]->request->get('parami') para una solicitud POST;

    donde [Request] representa toda la información sobre la solicitud recibida por el script web;

    17.10. Gestión de sesiones web

    En los ejemplos anteriores de cliente/servidor, el proceso era el siguiente:

    • el cliente abre una conexión al puerto 80 del servidor web;
    • envía la secuencia de texto: encabezados HTTP, línea en blanco, [documento];
    • en respuesta, el servidor envía una secuencia del mismo tipo;
    • el servidor cierra la conexión con el cliente;
    • el cliente cierra la conexión con el servidor;

    Si el mismo cliente realiza una nueva solicitud al servidor web poco después, se establece una nueva conexión entre el cliente y el servidor. El servidor no puede saber si el cliente que se conecta ha visitado el sitio anteriormente o si se trata de una solicitud por primera vez. Entre conexiones, el servidor «olvida» a su cliente. Por esta razón, se dice que el protocolo HTTP es un protocolo sin estado. Sin embargo, resulta útil que el servidor recuerde a sus clientes. Por ejemplo, si una aplicación es segura, el cliente enviará al servidor un nombre de usuario y una contraseña para autenticarse. Si el servidor «olvida» a su cliente entre conexiones, el cliente tendría que autenticarse con cada nueva conexión, lo cual no es viable.

    Para realizar un seguimiento de un cliente, el servidor procede de la siguiente manera: cuando un cliente realiza una solicitud inicial, el servidor incluye un identificador en su respuesta, que el cliente debe enviar de vuelta con cada nueva solicitud. Gracias a este identificador, que es único para cada cliente, el servidor puede reconocer a un cliente. A continuación, puede gestionar una entrada de memoria para ese cliente en forma de una entrada de memoria asociada de manera única al identificador del cliente.

    Técnicamente, así es como funciona:

    • En la respuesta a un nuevo cliente, el servidor incluye el encabezado HTTP Set-Cookie: Key=Identifier. Lo hace solo en la primera solicitud;
    • en las solicitudes posteriores, el cliente devolverá su identificador a través del encabezado HTTP Cookie: Key=Identifier para que el servidor pueda reconocerlo;

    Uno podría preguntarse cómo sabe el servidor que se trata de un cliente nuevo y no de uno que vuelve. Es la presencia del encabezado HTTP Cookie en los encabezados HTTP del cliente lo que se lo indica. En el caso de un cliente nuevo, este encabezado no aparece.

    Todas las conexiones de un cliente determinado se denominan «sesión».

    17.10.2. Ejemplo 1

    17.10.2.1. El servidor

    La gestión del ID de sesión es transparente para un servicio web. Este ID lo gestiona el servidor web. Un servicio web accede a la sesión del cliente mediante la función session_start(). A partir de ese momento, el servicio web puede leer y escribir datos en la sesión del cliente a través del diccionario $_SESSION. Si se utiliza la biblioteca [HttpFoundation], se puede acceder a la sesión mediante la expresión [Request→getSession].

    El siguiente código [session-server.php] muestra la gestión basada en sesiones de tres contadores. Con cada nueva solicitud, el script web incrementa estos contadores y los almacena en la sesión para que puedan recuperarse durante la siguiente solicitud.

    
<?php
// dependencies
require_once 'C:/myprograms/laragon-lite/www/vendor/autoload.php';
use \Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Session\Session;
 
//
// we retrieve the request
$request = Request::createFromGlobals();
// session
$session = new Session();
$session->start();
// three counters are retrieved from the session
if ($session->has("N1")) {
  // n1 counter increment
  $session->set("N1", (int) $session->get("N1") + 1);
} else {
  // counter N1 is not in session - create it
  $session->set("N1", 0);
}
if ($session->has("N2")) {
  // n2 counter increment
  $session->set("N2", (int) $session->get("N2") + 1);
} else {
  // counter N2 is not in session - create it
  $session->set("N2", 10);
}
if ($session->has("N3")) {
  // n3 counter increment
  $session->set("N3", (int) $session->get("N3") + 1);
} else {
  // counter N3 is not in session - create it
  $session->set("N3", 100);
}
// we work out the answer
$response = new Response();
// the content of the answer is utf-8 text
$response->headers->set("content-type", "application/json");
$response->setCharset("utf-8");
// the answer will be the jSON of an array containing the three counters
$response->setContent(json_encode([
  "N1" => $session->get("N1"),
  "N2" => $session->get("N2"),
  "N3" => $session->get("N3")]));
 
// reply sent
$response->send();

$requestPassword = $request->headers->get('php-auth-pw');

$response = new Response();

  // found - code 200
  $response->setStatusCode(Response::HTTP_OK);
}
// response has no content, only HTTP headers
$response->send();

    17.11.3. Protección de la conexión cliente/servidor

    Hemos visto que, para autenticarse con el servidor, el cliente envía el encabezado:

    authorization: Basic YWRtaW46YWRtaW4=

    Si esta línea es interceptada por un programa espía, este puede recuperar fácilmente las credenciales [nombre de usuario, contraseña] codificadas en Base64 dentro de la cadena [YWRtaW46YWRtaW4=]. Por este motivo, la autenticación debe realizarse a través de una conexión segura entre el cliente y el servidor. Las URL seguras utilizan el protocolo [HTTPS] en lugar del protocolo HTTP. El protocolo [HTTPS] es el protocolo HTTP dentro de una conexión cliente/servidor segura. Las URL seguras tienen el formato [https://chemin_document].

    No todos los servidores web aceptan URL con este formato. Deben modificarse para que sean seguras. El servidor Apache de Laragon es un servidor seguro, pero el protocolo HTTPS no está habilitado de forma predeterminada. Debes habilitarlo en el menú de Laragon:

    • en [4], habilita el cifrado SSL para el servidor Apache;

    Una vez hecho esto, el servidor Apache se reinicia automáticamente:

    • en [1], aparece un candado verde: esto indica que se ha habilitado el protocolo HTTPS;
    • en [2], aparece un nuevo puerto de servicio, el puerto 443 en este caso. Este es el puerto de servicio para el protocolo seguro HTTPS;

    Ahora que tenemos un servidor seguro, modifiquemos el archivo de configuración del cliente [config-auth-client.json] de la siguiente manera:

    
{
    "url": "https://localhost:443/php7/scripts-web/08/auth-server.php"
}

    En [2], el protocolo ha cambiado a [https] y el puerto a [443].

    El [HttpClient] de Symfony lanzó una excepción porque el servidor le envió un certificado de confianza que [HttpClient] no aceptó. La comunicación SSL se basa en certificados de confianza emitidos por autoridades oficiales. Cuando habilitamos el protocolo HTTPS en el servidor Apache de Laragon, se generó un certificado autofirmado para el servidor Apache. Un certificado autofirmado es un certificado que no ha sido validado por una autoridad oficial. El cliente [HttpClient] de Symfony rechazó este certificado autofirmado.

    Es posible indicar a [HttpClient] que no verifique la validez del certificado enviado por el servidor. Esto se hace utilizando opciones en el método [HttpClient::create]:

    
// on crée un client HTTP
$httpClient = HttpClient::create([
    'auth_basic' => ['admin', 'admin'],
    "verify_peer" => false
